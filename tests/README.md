# Battle verification

Run the local contract suite from the repository root:

```powershell
node --test tests/*.test.cjs
```

Runtime probes use the Maker server or client runtime, native `AttackComponent` / `HitEvent`, and `BattleSession`; JavaScript does not recreate combat.

Cardgame lobby probes, isolated storage-fault setup, cleanup and visual acceptance limits are recorded in [Issue #48](../docs/Issue-48-Lobby.md). They cover selected saved previews, empty groups, independent active selection, five selectors, draft isolation, preparation travel, queue/cancel and failure states through the production UI and services.

Tactical editor probes, isolated save tests, guarded 18-row catalog fixture, native wheel/input evidence and remaining human checks are recorded in [Issue #49](../docs/Issue-49-Editor.md). The #49 probes that edited a server-held working copy (`editor_flow`, `editor_failure`, `editor_native_input`) predate #50 and were retired with it.

Single-group saving, unsaved-change handling, the switch/leave confirmation, the mouse preview and the failure paths (explicit failure, unconfirmed timeout, late reply) are recorded in [Issue #50](../docs/Issue-50-Editor-Save.md). `editor_save_flow_runtime_probe.lua` (client) covers the happy path and every control state; `editor_save_failure_runtime_probe.lua` (client, edit its first `MODE` line) covers `FAIL`, `SILENT` and `LATE` storage acknowledgements, with the matching `ConfigureMakerSaveResponse` set and reset from `server_main`. Both need a fresh Play and, first, an isolated `_FormationService.StorageKey` set in `server_main`.

The editing rules (unsaved changes, the save / switch / leave decision, block reasons, placement) live in `FormationEditSession`; `FormationLobby` only draws its state and carries out the commands it returns. `edit_session_runtime_probe.lua` (client, fresh Play) drives that module with synthetic snapshots — no UI clicks, no server round trips, nothing saved — and finishes with `[VRF][EditSession] PASS`.

`formation_save_rejected_runtime_probe.lua` 在 `server_main` 的單玩家全新 Play 執行，不改儲存鍵、不寫 DataStorage。驗證 stale revision、七單位、錯組與 pending 狀態的請求都回覆可正確關聯的 `REJECTED`，拒絕不改五組內容、版本、出戰選擇或寫入狀態；pending 是暫時的記憶體夾具，結束時連同回覆與訊息一併還原。此探針不驗證實際在途寫入與持久資料讀回。需等待 `[VRF][Save50R] PASS`，不能把派送成功當成通過。`editor_preview_cards_runtime_probe.lua` 另驗證放置模式不新增 hover、重新選卡會清除既有 hover、取消放置後恢復 hover；同樣需要隔離空存檔，在 `client` 執行。

`formation_placement_runtime_probe.lua` verifies shared 0.3 spacing, fractional positions, mirroring, existing document encoding, and production deployment in `server_main`; it removes its deployed fixtures afterwards. `centered_terrain_runtime_probe.lua` checks the template, simulation and lobby terrain in the same Play session. The local contract suite compares every map's terrain and coordinate transform with `map/template.map` so inconsistent developer-authored maps fail verification.



The earlier five-slot, empty-return, delayed / failure / relogin and handoff-late-leave formation probes (`formation_slots_*`, `formation_empty_return_runtime_probe.lua` and the rest of that family) were retired when #50 moved unsaved changes to the client, because the draft behaviour they drove no longer exists. [Issue #50](../docs/Issue-50-Editor-Save.md) lists them; [Issue #29](../docs/Issue-29-Formations.md) keeps their original evidence as history. Current coverage is the #50 probes above.

The two-player battle HUD, own result and return flow are recorded in [Issue #51](../docs/Issue-51-Battle-HUD.md). `matched_battle_result_ui_runtime_probe.lua` runs in `client` and must be dispatched after the player enters the match, because moving rooms resets the client context.

Lobby-only matchmaking, waiting/cancellation locks, five saved groups and the full return flow are recorded in [Issue #52](../docs/Issue-52-Match-Flow.md). `match_flow_runtime_probe.lua` runs in `client`; `match_flow_roundtrip_runtime_probe.lua` runs in `server_main` after the real client's queue is confirmed. The latter retains detached expectations until both players have returned and their formation sessions are initialized. Use the same handoff storage key in every room, isolate formation saves, and reset every injected fault afterwards. Native screenshots and real-mouse / published-instance acceptance limits are listed in that document.

`match_recovery_runtime_probe.lua` runs in `server_main` with one lobby player, owns unique formation/handoff keys, and restores its faults and keys afterwards. Run `RESERVE` and `CANCEL` to check cancellation retries after a late durable write without an intervening status/read. For a silent formation save, run `editor_save_failure_runtime_probe.lua` phase 1, reset the fault, then run phase 3 to confirm, discard and return without saving again. Repeat with `EXISTING=true` and an isolated saved one-unit group 1 to cover `READY` as well as `NEW`. `edit_session_runtime_probe.lua` also checks that pending/failed reconciliation keeps leaving blocked.

Cancellation response failures use the production `CancelMatching` boundary: arm `ConfigureMakerCancelFaults(1, 1)` in `server_main`, then run `match_cancel_runtime_probe.lua` in `client` (`MODE='FAILURE'`). With the hf2602 peer and the same isolated formation key, run `match_cancel_race_runtime_probe.lua` in `server_main` using `SUCCESS`, `SEAL_FAILURE`, and `ENTRY`. The sealing modes wait for the coordinator's `SAVING` phase. Dispatch client `PROGRESS` before `SEAL_FAILURE`, and client `ENTRY` after server `ENTRY`; reset the movement fault after the visible abort and return the peer too. Keep the default handoff key across rooms. `match_cancel_reconnect_runtime_probe.lua` runs in `server_main` with one lobby player and its own storage keys; it reconnects during disconnect cleanup with a successful and then a failed cancellation, and cancels a durable-only ticket, checking that no lock is stranded and that a failed cleanup is recovered rather than left unlocked.

After a normal match admits both players, set the same isolated formation key in its instance and arm `ConfigureMakerFaults(0, 1, 0)`. `matched_battle_return_save_runtime_probe.lua` waits for the natural result and verifies the failed return save and visible retry; confirm lobby arrival from the new client context. Run `match_cancel_disconnect_runtime_probe.lua` last with an idle hf2602 to check the shared `Depart` cleanup command, then restore every injected fault, storage key and original formation session before stopping Play. These are Maker boundary injections, not published native-service or physical-mouse acceptance.

## Maker runtime procedure

For each combat runtime probe listed below, use a fresh Play test. Stop, clear logs, Refresh, read build logs, then Play and wait until `template` reaches `DEPLOYMENT`. Pass the entire Lua file to `maker_execute_script` with `context=server_main`, except the client probes identified below. A successful script dispatch is not a passing test: read normal logs until that probe's final `PASS` or `FAILURES=...` marker appears. Inspect all build and normal Error / Warning entries. The only expected diagnostic in this suite is the single `unsupported attack profile` message intentionally caused by the first invalid-profile case in `attack_execution_runtime_probe.lua`. Stop after each combat probe.

## Deployment scroll preview

Maker Play starts with 18 display cards by repeating the server's catalog on the client. The first three keep their original names; extra copies have numbered labels and deploy the corresponding original `MonsterId`. `MonsterData.csv` and combat values are unchanged. Published play always uses the original catalog.

Use the preview toggle in the deployment panel to return to the original three cards or show 18 again. Set `BattleDeploymentInput.PreviewCardCount` to `0` to start Maker Play without the preview. Cards fill a fixed five-column grid (18 cards make four rows) inside an 812px-wide viewport; the deployment panel is 1240px wide. Scroll with the mouse wheel, or drag vertically using the cards or right-side scrollbar. The scrollbar automatically hides when all cards fit. These controls currently target the POC's PC mouse input.

Run `deployment_scroll_runtime_probe.lua` in a fresh client Play with the formal catalog and zero deployed player units. It verifies connected button events, native layout/scroll positions, selected-copy labels, original-ID deployment/removal, and destruction of previous cards after toggling. It restores the original preview count and leaves deployment open. Drag gestures and visual scrollbar readability still require real PC input. The formal six-versus-six and variant UI probes turn off the preview before checking catalog counts.

The native scrollbar uses `BottomToTop` so its handle starts at the top. The MSW scroll API still reports top=0 and bottom=1 independently of that handle direction. The viewport has a transparent raycast surface so wheel input continues over card gaps with a stationary cursor. `deployment_scroll_wheel_runtime_probe.lua` verifies the native wheel path through `maker_mouse_input`, including the first gap that previously swallowed wheel events. Change its `expectedEvents` to 38 for the longer reproduction, or set `startAtBottom=true` and send positive deltas to test upward scrolling. On this Maker version each wheel delta unit moves 30 UI pixels, so the 13-event case must travel 78px and the 38-event case 228px. It releases its event connection and timeout after either result.

Keep the 250ms interval so Maker has time to process each simulated wheel input between observations. The same 38-event sequence at 250ms reproduces the missing-hit-surface bug: without the viewport renderer it stops at 72px; with the renderer every event advances, totaling 228px.

`ResetScrollPosition` readback settles on the following frame. The wheel probe measures from the requested endpoint, rather than immediately reading a stale offset left by an earlier probe.

## Temporary MonsterData identity case

Only the dedicated identity / independent-stat cases change `RootDesk/MyDesk/Data/MonsterData.csv`. Run them as a guarded transaction using `withTemporaryMonsterCsv` from `monster_catalog_csv_fixture.cjs`:

1. Stop Maker and copy the original CSV bytes to a unique directory under the operating system temp directory. The guard records byte length and SHA-256, verifies the backup, and writes a temporary fixture with byte-checked output. The default fixture changes `monster_tank` to `RenamedTank` and adds a row cloned from the tank with only `MonsterId=probe_tank_variant` and `MonsterName=VariantTank` changed. For the independent-stat case, pass `variantStats: { MaxHp: 650, MoveSpeed: 0.7, AttackDamageMin: 25, AttackDamageMax: 25, AttackIntervalSeconds: 1.3, AttackRange: 0.8, ContactCooldownSeconds: 1.3 }`; original-row statistics and all resource cells remain unchanged.
2. Refresh, read build logs, start a new Play test, then execute the complete `monster_catalog_identity_runtime_probe.lua` in `server_main` for the default fixture. It queries the loaded catalog, compares the profile fields, checks the official options, and deploys both IDs through `TryDeployMonster`. For the independent-stat fixture, execute `monster_catalog_variant_runtime_probe.lua` in `server_main`, require PASS, then Stop and start a separate fresh Play test for `monster_catalog_variant_ui_runtime_probe.lua` in `client`. Require its PASS before leaving the fixture stage.
3. The guard requires Maker Stop, Refresh, and restored-catalog verification callbacks before it changes the CSV. When the probe succeeds, fails, throws, or receives a graceful SIGINT / SIGTERM / AbortSignal, it waits up to 30 seconds for an interrupted probe callback to settle, then awaits Maker Stop, gives the probe one more bounded chance to settle, restores the saved bytes, verifies byte equality and SHA-256, awaits Refresh, and runs the supplied restored-catalog verifier. Each Maker lifecycle callback has a 120-second timeout. Signal handlers remain active through the final Stop. If cancellation, logging, or a lifecycle callback times out or fails, the guard still attempts restoration and verification but retains the temp backup and reports incomplete cleanup with its path; it never reports that transaction as successful.
4. The restored verifier uses a fresh Play test and the complete `monster_catalog_restored_runtime_probe.lua` in `server_main`; require its final PASS, then Stop. It checks `monster_tank` is again named `Tank`, the temporary ID is absent, the option count is three, and the session is in formal deployment.

The helper takes Maker lifecycle callbacks so filesystem rollback and Maker Stop / Refresh / catalog verification use the same `finally` path. The temporary row, renamed name, backup, and manifest are not tracked or committed. Neither identity probe needs a manual clock or real movement frames.

`node tests/monster_catalog_fixture_driver.cjs` supplies the independent-stat fixture and a line-based bridge for an MCP orchestrator. Each JSON request has an increasing `id`, `request`, and `details`. Complete the actual Maker operation and require the runtime verdict before writing `{"id":<matching request id>,"ok":true}` to its stdin; report failures with the same ID, `ok:false`, and `error`. The `variant-probe` request covers both independent-stat probes above. `restored-probe` covers a fresh Play and `[M1][CatalogRestoreProbe] PASS`. The driver asks for Stop separately before installation, before restoration, and after restored verification. A cancelled probe rejects its pending request; a late acknowledgement with that probe's ID cannot acknowledge cleanup Stop. Overlapping requests are rejected. `[VRF][CatalogFixture] PASS` is emitted only after the complete guarded transaction succeeds.

## Regression evidence

After restoration, re-run `node --test tests/*.test.cjs`, `deployment_runtime_probe.lua`, and `six_vs_six_full_battle_probe.lua` in separate fresh Play tests. Keep the formal battle within 45 seconds, require exactly one legal RESULT, and wait one additional real second to verify HP, combat serials, target, position, and knockback state remain stable. Capture the restoration SHA-256, the restored-catalog PASS, and each runtime verdict before concluding the fixture is clean.

The probes assert observed HP, `DamageTakenSerial`, `OnHitSoundSerial`, `AttackSerial`, events, positions, and results. Source-string assertions remain for structural contracts only; they do not substitute for runtime evidence.

Controlled contact scenarios pin `AttackDamageMin = 40, AttackDamageMax = 40` when their literal HP expectations require it. The formal catalog uses its configured damage intervals. Motion behavior is verified through the session and existing actor observations; the former source-string assertion about where knockback lived has been removed.

For #55, `attack_execution_runtime_probe.lua` samples each attack type 32 times using an 8–9 interval, checking both endpoints, variation, native `HitEvent` / `HIT` / `DAMAGE` amounts against HP loss, and independent rolls for area targets. The receivers' native Bodies are held while the existing manual attack clock advances, so real-frame tank knockback cannot move the damage fixtures out of contact. Existing cancellation, range and tank contact rules remain covered until their separate attack-rules tickets land. Catalog validation covers both damage fields, reversed bounds and equal endpoints. The intel and tooltip probes compare the entire `min～max` text through real card selection and hover events.

For #56, the attack probe checks 28 exact-contact/separation cases across both attack types and both facing directions. Binary-fraction collider fixtures cover X, upper/lower Y and corner boundaries; the same full battle step observes engagement and native damage. It also checks misses behind a locked facing, movement suppression through the animation, and a single long actor step that crosses both impact and animation-end deadlines. Real-frame motion tests cover diagonal approach, vertical-only alignment, stopping and native hits for all three types. Quiet fixtures use long attack intervals instead of zero range; a zero range remains permitted by the existing Maker override seam. Warrior area damage, shooter cancellation policy and tank contact damage remain for their later tickets.

For #57, warrior and shooter hit only the target locked when the attack started. `attack_execution_runtime_probe.lua` covers a beside-target decoy, a locked target leaving with another enemy still in range, and a locked target dying first: each is a whiff that deals no damage, keeps one `AttackSerial`, plays out the animation and consumes the interval. Only actor stop and reconfiguration cancel an attack, and both clear the interval for every type.
