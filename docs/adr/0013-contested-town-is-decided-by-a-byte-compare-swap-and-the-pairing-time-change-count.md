# 同時爭城由城鎮文件的位元組比較寫入裁決，免扣兵力由配對時的換旗次數判斷

兩場戰鬥爭同一座城時，要保證兩件事：同一個鼓山剩 20 的畫面下，只有實際使城鎮易主的那一場能扣兵、推進、觸發失城撤退；配對成功後任一出戰城曾換旗（即使被奪回）的場次，兩城都不扣兵，但勝敗與怪物經驗照舊。ADR 0010、0012 留下的缺口是同一個：城鎮文件是讀取—修改—寫入，沒有比較並寫入，結算端也不知道「配對時的世界」長什麼樣。

## 決定一：排他靠原生條件更新，不靠鎖

`FactionWar:SwapTowns(expected, towns, complete)` 只在儲存裡的位元組仍等於當初讀到的位元組時才寫入：

- `FactionWar:ReadTownsRaw` 讀出解碼後的城鎮表與原始位元組（尚未寫過時位元組為 nil）；`ReadTowns` 是它的包裝，所以所有讀者看到同一份文件。
- 文件已存在時走 `FormationStorage:Swap`，直接用原生 `UpdateAsync(key, expectedValue, newValue)`，不取任何 guard。位元組不同回 `2000000`（`1000002` 也併入同一個代碼），`SwapTowns` 翻成 `CONFLICT`；其他非零代碼是 `FAILED`。
- 文件尚不存在時（世界第一次結算）才走 `Write` 的受 guard 建立路徑（取 guard、重驗不存在、`SetAsync`）；兩個同時的第一次寫入只有一個會成功，另一個回 `CONFLICT`（guard 被占用 `1000007` 或重驗時文件已存在）。
- `FormationStorage` 以保留前綴 `global:<儲存名稱>` 認得全域表（`FormationStorage:Storage`），讀、寫、guard、timeout 後的 guard 釋放與 Maker 故障注入（`ConfigureMakerFaults`）因此與預存編隊、怪物等級共用同一條邊界。玩家 profile 碼不會以 `global:` 開頭。

`FactionWarAttack:Attempt` 先讀位元組、依該次讀取決定結果、再以那份位元組換入；`CONFLICT` 代表別場先寫，輸家 0.3 秒後重新讀取並重新決定：它可能發現城鎮已被奪走（成為免扣兵，見下），也可能只是兵力被別場扣過而照樣再扣一次（所以非奪城的同時結算不會互相蓋掉）。`SettleConflicts`（10）與原本的失敗上限 `SettleAttempts`（4）各自有界，用盡回 `FAILED`。一份文件的位元組每次結算都會多一筆不重複的 `settled` 紀錄，所以不會出現位元組回到舊值的 ABA。

**不選**：

- 共享記憶體互斥鎖包住整段讀改寫：WorldInstanceSharedMemory 確實跨 world instance，但鎖沒有逾時。持鎖的結算房被回收、或釋放呼叫逾時而 `_T.releases` 隨房間消失，鎖就永遠停在 `writing`，之後全世界每一場戰果的寫入都被擋住，直到所有實例重啟。預存編隊的 guard 只會擋一位玩家，城鎮文件是全世界共用的，風險不同。所以已存在的文件不取 guard，只有第一次建立才取，且那次的殘留 guard 由同一房間下一次對該文件的讀取釋放。
- 由靜態房單一結算者序列化：跨 world instance 做不到，也讓戰果依賴另一個房間的存活。
- `TransactSetAsync`：原子但沒有條件，無法表達「僅當沒人先寫」。
- 每城一份文件：奪城要同時改勝方紀錄與敗方城，仍需要同一個條件式提交。

## 決定二：換旗次數與配對時的蓋章

城鎮文件每座城多一個選填整數 `e`（換旗次數）。缺少視為 0，只有奪城那次寫入把敗方城改成 `{ owner, strength = 100, e = 舊值 + 1 }`，其他城原樣照抄；`DecodeTowns` 拒收負數、小數與非數字。主城不會換旗，不會有 `e`。次數只增不減，所以「與配對時不同」就等於「這段時間內換過旗」，被奪回也看得出來（歸屬一樣、次數多了 2）。

配對成立時（`MatchFlow:Matched`，守衛配對與真人配對都經過它），`FactionWarAttack:Snapshot` 讀一次城鎮文件，記下兩座出戰城當時的次數，`Stamped` 把 `homeEpoch`、`awayEpoch` 放在配對的**複本**上（本機 adapter 的 `matches` 表是兩個玩家共用的同一個表，不能改它）。這個複本照原路徑進 `FormationHandoff:Commit` 與票券的 `match`，重新登入與換房間後仍在。同一張票券的第一次讀取為準（`ticket.snapshot`），延後後恢復的配對不會重蓋章。真人戰兩張票券各自在自己的協調者蓋章，`RoomBattleAdmission` 以 `FactionWarAttack:Combine` 取兩者較小值（較早的讀取）交給 `MatchedBattle`，結算時當作 `Settle` 的最後一個選填參數。

結算時 `ChangedSince(snapshot, 主場城, 客場城, 城鎮表)` 只看這兩座城的次數是否與蓋章不同。不同就回 `EXEMPT`：不寫儲存、不扣兵、不奪城、不推進、不通知失城。勝敗與怪物經驗不經過 `Settle`（`BattleSession` 在產生結果時結算，`MatchedBattle` 先對所有玩家發布結果、再呼叫 `Settle`），所以免扣兵的場次仍保有勝、敗、平與陣亡經驗。

判斷順序固定為：先找 `settled`（已套用過的場次回 `DUPLICATE`），再判 `ChangedSince`，再判舊的同陣營 `SKIPPED`。順序不能反：奪城的那場自己寫入後城鎮次數就變了，重送時若先判免扣，就會把自己當成別人的失效戰果，丟掉「這場奪了城」的紀錄。

**不選**：

- 只比對結算時的歸屬：看不到「被奪走又奪回」，且兩座城都換過旗時 `owner = towns[勝方城].owner` 會取到錯誤陣營（ADR 0012 留下的極端情形）。有蓋章的場次在算新歸屬之前就已排除。
- 把配對寫進城鎮文件再逐場清理：每場配對多一次全域寫入，還要清理。
- 在 `MatchedBattle` 入場時才蓋章：晚於配對，漏掉配對與入場之間的換旗。

**沒有蓋章的場次**（大廳配對不需要；讀不到城鎮文件的配對；本改動之前寫下的票券）維持舊判斷：勝負城歸屬相同則 `SKIPPED`，其餘照扣。這類場次遇上「奪走又奪回」或「兩城都換旗」仍可能扣兵，是已知缺口，範圍只限讀取失敗與升級當下已在途的配對。

## 紀錄與重送

`settled` 紀錄形狀不變（`{ k, w, l, s, o }`，上限 20 筆，整份文件仍小於一個儲存額度，加上最多兩個 `e` 欄位後以探針量測）。`EXEMPT` 不留紀錄：次數只增，重送時重新判斷必得到同一答案，也就不需要為「什麼都沒改」多寫一次。`DUPLICATE` 仍帶出當初的 `s`、`o`，`Finish` 對重送的奪城再通知一次失城清空（掃描對重複通知是冪等的，見 ADR 0012）。寫入逾時（`1000004`）不知道有沒有生效時，下一次讀取若看到自己的紀錄就回 `DUPLICATE`，沒有就依新位元組重算，所以重試最多讓兵力、歸屬、落點各套用一次；經驗值仍由 `MonsterLevelStorage` 的 CAS 與 `settled` 清單負責。

## 落點

不變：`MatchFlow:MoveHome` 在玩家按返回時問 `FactionWarAttack:LandingFor`，以結算結果與**即時**城鎮表決定。免扣場次的 `outcome.flipped` 為 false，所以沒有人推進；出戰城屬己方就留在該城（包含被奪走又奪回的情形），屬敵方就回自己的主城。每次返回都重新讀陣營與城鎮表（失敗時先重讀 `LandingReadAttempts` 次再退回出發城），不快取上一次的落點，重試返回就看得到最新歸屬。如果另一場的奪城在這位玩家已落地之後才寫入，靜態房的失守清空（ADR 0012）會把他送走。

## 已知缺口

- 結算寫入用盡重試後回 `FAILED`，沒有人在之後重新送出（`Settle` 內舊註解寫的「留給下一次戰果送達」從來不是事實，已移除）。`MatchedBattle` 只送一次。
- 原生 `UpdateAsync` 比對失敗的代碼以 `2000000`／`1000002` 判讀；若環境回報別的代碼，結果只是走較慢的失敗重試（1 秒一次，最多 4 次），不會寫錯。Maker 探針會量出實際代碼；發布環境兩個 world instance 同時結算尚未驗證，留給 #110。
- 世界第一次寫入仍用 guard；若建立逾時而房間在讀取確認前被回收，殘留的 `writing` 會擋住之後的第一次建立（已存在的文件不受影響）。實務上第一次結算前文件多半已由初始化或前一場寫入。
- 蓋章讀取與配對成立之間有一段（一次 adapter 回覆與一次城鎮文件讀取）換旗是看不到的；真人戰兩張票券各自蓋章，兩次讀取之間的換旗以較早的那次為準。
- 清單上限 20 筆：超過 20 場之後才重送的舊戰果，不會被認出是重複。
